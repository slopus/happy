## 2. 产品定位

一个由用户组织的 Agent 群聊工作台：先配置数字员工的名字、角色与模型，再把成员邀请进群，通过自然语言和内联 `@` 协作。

主时间线看「谁说了什么、发现什么问题、给出什么结果」；需要追溯时再展开某位 Agent 的执行细节。群聊不固定金融领域，不要求填写股票、周期或分析方法。

不设置强制主持人，也不强制所有讨论经过「检查环境 → 独立分析 → 交叉讨论 → 汇总观点」。用户可以随时插话；一次提问可以只找一人，也可以同时找多人。

## 4. Agent 与群的关系

### Agent 配置

用户已确认的设计意图：Agent 可以预先配置并复用，包含显示名称、角色说明及对应模型。Agent 管理页的具体表单未出现在本截图中，不把未展示字段布局当成定稿。

截图展示的示例角色：

| 角色 | 关注点 |
| --- | --- |
| 产品经理 | 用户需求与产品价值，判断问题是否值得解决，再给出最小可行方案 |
| 技术负责人 | 实现成本、技术约束和开发路径，把想法拆成可验证的小步骤 |
| 质疑者 | 风险、漏洞和反例，对未经验证的假设提问，而不是为反对而反对 |

这些是示例，不是系统固定岗位。截图中的 Claude / Codex 表示当时的多引擎设计意图；当前实现统一使用 Codex，不能据此声称已支持 Claude。

### 群配置

群由主题和成员组成，用户在群内发送任务。角色配置与群成员身份分开：同一个 Agent 配置可以被邀请到不同群，各群上下文独立，不自动共享其他群的内容。

新建群不应要求填写某一行业的复杂参数。具体创建表单和成员弹窗未在截图中展开；不能从截图推断已实现动态退群、改名或热更新角色。

## 5. 消息与指派规则

### 内联 @

- 在输入框中通过 `@名字` 指定一位或多位成员，不依赖独立的收件人下拉框。
- 有显式 `@` 时，优先交给被点名成员，不自动让未点名的成员全部回答。
- 例：`@产品经理 @技术负责人 帮我看看这个想法是否值得做，以及最小实现方案。`
- 发言下面展示类似「被你 @ 点名」的来源提示，让用户知道为什么是这个 Agent 回复。
- 候选菜单的键盘选择、同名成员和非法 mention 的具体反馈，截图没有展示，不作为已验证交互。

### 自动接话

- 无 `@` 且自动接话开启时，按话题选择相关成员。
- 截图规则卡明确说明草图使用关键词模拟选人，不会让所有成员轮流回答。因此该草图不能证明已经存在模型驱动的智能路由。
- 「仅 @ 回复」是关闭自动接话时的设计模式：普通消息进入记录，不要求 Agent 自动发言。
- 自动接话不等于自动辩论，更不意味着无限循环。后续加入的有界辩论见第 9 节。

### 成员请求协助

「成员请求协助」是截图中的示例入口，体现 Agent 可请求其他成员帮助的产品方向。截图没有展示执行结果，不能据此认定已打通 Agent 自主委派或跨 Agent 调度。

## 6. 时间线与执行细节

每条 Agent 发言应能辨认作者、角色/引擎、时间与正文；模拟内容明确标识「预设示例」。正文允许段落和列表，以结果为主要内容。

「查看执行细节」是渐进展开入口：用户不需要先阅读技能、浏览器和工具调用才能理解回答，但需要时可以追踪原始执行。主时间线不展示凭据或隐藏推理。具体详情抽屉、字段和返回动作未在截图中展示。

群公开发言与 Agent 私有执行记录是两种信息，不能把工具输出直接当成群消息。用户可以同时看到整体讨论和某个成员的执行过程，而不是只能看黑盒结论。

## 7. 输入与视觉语言

- 输入框引导：「说点什么，或输入 @ 邀请一位、几位成员回答…」。
- 支持图片与文字共同表达；截图没有展示上传完成、删除附件、失败或文件限制，相关细节以实现契约为准。
- `Enter` 发送，`Shift + Enter` 换行；发送按钮在输入框右下方。
- 「@ 两位成员」「不 @，自动接话」「成员请求协助」是帮助理解机制的示例入口，不应成为强制步骤。
- 截图使用深色背景、细分隔线、紫蓝强调色、不同角色的彩色头像。中央文本区域留白较多，避免所有回复都包在大气泡中。
- **用户后续已要求整体偏亮。** 本图归档的是布局、层级与交互参考，不表示撤回亮色偏好。后续实现需使用项目语义主题色，同时保证正文、辅助说明、边框和操作态对比度；不要从截图复制硬编码色值。
- 仅有桌面宽屏依据；移动端布局和窄屏折叠规则没有在本图中定稿，不扩展为 Tauri 桌面客户端要求。

## 8. 典型使用路径

1. 在 Agent 管理中配置成员的名字、职责和模型。
2. 新建一个群，邀请需要的 Agent，不要求指定主持人或行业流程。
3. 发送普通消息；根据自动接话开关决定是否由相关成员回答。
4. 输入 `@产品经理 @技术负责人` 并描述需求，让两位成员参与。
5. 在统一时间线阅读观点；需要时点某条发言的执行详情。
6. 用户补充、纠正或切换讨论方向，无需重新走固定分析流程。

这是已讨论的产品路径；截图只直接提供群聊主界面证据，不等于上述每个页面都已视觉验收。

## 10. 后续实现核对清单

- 用户进入群后，能直接理解群主题、成员身份和自动接话状态。
- 不通过额外收件人下拉框也能 @ 一人或多人。
- 公开时间线聚焦发言；执行过程按需查看，不能用泄露凭据或隐藏推理来补足「细节」。
- 未点名的消息不会默认触发所有成员轮番回答。
- 新建讨论不捆绑金融参数或固定阶段。
- 草图模拟声明与生产真实运行状态各自准确，不能把预设回复当成真实验收。
- 亮色偏好与主题适配保留，不能因保存了深色参考图而改回强制深色。
- 超出本截图的创建弹窗、Agent 表单、详情态和窄屏设计，实施时另行确认，不自行标为已定稿。

用户已确认一起修复当前群聊页面与创建弹窗的视觉差距、机器名称不可读问题：
