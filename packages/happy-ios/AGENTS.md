# happy-ios

Native iOS client for Happy, written in Swift with UIKit. It ports
`packages/happy-app` (React Native) screen by screen. It is not shipped yet:
nothing here is wired to the release skill or to EAS.

## Rules

1. **UIKit only, never SwiftUI.** No Core Data, SwiftData or CloudKit.
   Persistence is SQLite through GRDB (or raw SQLite).
2. **Dependencies come through SwiftPM only.** Never CocoaPods, Carthage or
   vendored frameworks.
3. **Build and test with `xtool` and `swift` on machines that aren't Macs.**
   On a Mac, use Xcode.
4. **The Xcode project is generated by XcodeGen from `project.yml`.** Never
   commit a `.xcodeproj` or edit one by hand.
5. **Measure every component and test its layout.** Layout is deterministic
   manual frame layout:
   - `HappyLayout` holds the layout logic. It is pure Swift and imports only
     Foundation, plus CoreGraphics on Apple platforms. Each layout is a
     function from inputs (container size, safe-area insets, measured
     content sizes) to frames.
   - Views in `HappyUI` only measure their content (`sizeThatFits`) and
     apply the computed frames in `layoutSubviews`. A view must not contain
     arithmetic that decides where something goes.
   - Every layout has exact-frame tests in `Tests/HappyLayoutTests`. They
     run on Linux.
   - Anything that needs UIKit to measure goes in `Tests/HappyUIKitTests`.
     That target compiles to nothing on Linux and runs only in the iOS
     simulator.

## Scope

- **Latest Happy protocol only.** There are no legacy code paths.
  `packages/happy-wire` and happy-app's current sync code
  (`packages/happy-app/sources/sync`) are the source of truth. When they
  disagree with this package, this package is wrong.
- **No voice mode.**
- **Offline first.** Everything the account has is kept in the local
  SQLite store, and the UI reads only from that store. The network only
  moves deltas:
  - sessions changed since a cursor;
  - messages after a session's last synced `seq`;
  - versioned settings, changed locally as a pending delta that is pushed
    with `expectedVersion` and re-based on the server's copy on conflict;
  - the profile and the projects sessions point at, fetched whole;
  - an idempotent outbox for writes.
- **Tool outputs are hidden by default** when chat lands.
- **Onboarding follows happy-app step by step.** Signed in, home decides
  from the stored machines (`HomeState`, after happy-app's
  `shouldShowFirstRunInstall` and `resolveHomeEmptyState`):
  - a spinner until machines have been fetched once. An empty store is
    "not known yet", so an account restored or upgraded from the RN app
    is never asked to link a computer it already has;
  - Link Your Computer when there are none;
  - the offline checklist when none is reachable and nothing is listed
    (with "Show archived" when there is an archive);
  - "No sessions yet" on a reachable computer with no sessions;
  - the session list otherwise, even while every computer is offline (the
    offline plaque heads it then).

  The session list is a `UITableView` over `SessionList` (happy-app's flat
  grouping): live rows by activity, the archive toggle, archived rows by
  day. Swipe or long press archives (`SessionActions`: `killSession` over
  `rpc-call`, then `POST /v1/sessions/:id/archive`). A tap only marks the
  row read until chat lands. Local-only row state (`thinking`, `unread`,
  `archiving`) lives on the session row and follows `LocalStore.settle`.

  Home stays the navigation root and swaps its content, so screens pushed
  over it stay put when a computer arrives.
- **Credentials stay in the RN app's Keychain item.** This app reads and
  writes happy-app's `auth_credentials` exactly as expo-secure-store 55
  stores it, so an in-place upgrade (same bundle ids) stays signed in and a
  rollback to an RN build still works. Never copy credentials into an item
  of our own, and don't change the item's layout:
  - generic password, service `app:no-auth`;
  - account and generic set to the UTF-8 bytes of `auth_credentials`;
  - `kSecAttrAccessibleWhenUnlocked`, the default access group;
  - the value is the UTF-8 of `JSON.stringify({ token, secret })`.

  Reads go `app:no-auth`, then `app:auth`, then legacy `app`. Writes add to
  `app:no-auth` (updating on a duplicate) and then delete the other two.
  Logout deletes all three. `Sources/HappyCore/Auth/SecureStore.swift`
  implements this behind `KeychainBackend`, and `SecureStoreTests` pins it
  on Linux. Any other iOS-only secret gets its own item and must never
  touch this one.
- **Copy comes from happy-app.** English strings are copied verbatim from
  `packages/happy-app/sources/text/translations/en.ts` into
  `Sources/HappyUI/Strings.swift`.
- **Design tokens come from happy-app.** They are ported from `theme.ts`
  and the component stylesheets (iOS values) into
  `Sources/HappyLayout/DesignTokens.swift`.

## Layout

| Target | Platforms | What it holds |
| --- | --- | --- |
| `HappyCrypto` | all | Key tree, X25519 box, XSalsa20-Poly1305 secretbox (pure Swift), AES-GCM, Ed25519, secret key backup format. CryptoKit on Apple, swift-crypto on Linux. |
| `HappyWire` | all | Wire types: API payloads, update and ephemeral events, the session protocol, pairing links. |
| `HappyStore` | all | GRDB schema, records and the merge rules: versions only move forward, deletes are explicit. |
| `HappyCore` | all | Server config, HTTP API, auth, QR login, pairing, record decryption, the delta `SyncEngine`, Socket.IO client, `AccountSession`, `AccountController`, and what home shows (`MachineChoice`, `HomeState`). |
| `HappyLayout` | all | Pure layout functions, design tokens, the wordmark's vector paths. |
| `HappyUI` | iOS (UIKit) | Views, screens and the coordinator. Wrapped in `#if canImport(UIKit)`. |
| `HappyApp` | iOS | `@main` AppDelegate, SceneDelegate and the composition root. |

Products:

- `HappyApp` is the app that xtool packages.
- `HappyKit` is everything else. The XcodeGen app target compiles
  `Sources/HappyApp` itself and links `HappyKit`.

## Build and test

### Linux

The toolchain is Swift 6.x. The GRDB build needs the `libsqlite3-dev`
headers.

```sh
swift build --build-system native
swift test --build-system native         # everything except HappyUIKitTests
```

`--build-system native` is used because the newer swiftbuild backend has
been seen to hang in sandboxes.

To build for iOS with the Darwin SDK from `xtool sdk`:

```sh
swift build --build-system native --swift-sdk arm64-apple-ios
swift build --build-system native --swift-sdk arm64-apple-ios-simulator --build-tests
xtool dev build                          # packages xtool/HappyApp.app (dev bundle id)
xtool dev run                            # needs `xtool auth` and a connected device
```

xtool reads `xtool.yml` and packages the dev variant only. Notes:

- If SwiftPM can't find the SDK (it resolves `~` through the passwd
  entry), pass `--swift-sdks-path <dir containing darwin.artifactbundle>`.
- xtool has no test runner and Linux has no simulator, so
  `HappyUIKitTests` can be built here but not run.

### macOS

```sh
brew install xcodegen
xcodegen                                 # writes Happy.xcodeproj (git-ignored)
open Happy.xcodeproj
```

Schemes:

| Scheme | Builds | Archives |
| --- | --- | --- |
| `Happy` | Debug (dev) | Release (production) |
| `Happy (preview)` | Preview | Preview |

The `Happy` scheme's test action runs `HappyUIKitTests` on a simulator. The
Linux test targets also run from Xcode: open `Package.swift` and use the
`HappyIOS-Package` scheme.

### Variants

| Variant | Configuration | Bundle id | Name |
| --- | --- | --- | --- |
| development | Debug | `com.slopus.happy.dev` | Happy v2 (dev) |
| preview | Preview | `com.slopus.happy.preview` | Happy v2 (preview) |
| production | Release | `com.ex3ndr.happy` | Happy v2 |

The bundle ids are the RN app's. Each variant has its own
`App/Info-*.plist`. Those files are plain plists, because xtool doesn't
expand `$(VARIABLES)`. `AppConfigurationTests` keeps their shared keys
identical and checks the variant keys:

- display name;
- `HappyAppVariant`;
- ATS: local networking everywhere, arbitrary loads outside production.

Only production has entitlements (associated domains).

### Versioning

This app uses a new versioning scheme, separate from happy-app's semver
(`1.x.y`): **`vYYYY.MM.N`**, where `N` counts releases within that month,
starting at 1 (e.g. `v2026.10.1`). The "v2" in the display names likewise
tells it apart from the legacy RN app.

- `CFBundleShortVersionString` must be integers only, so it holds the
  version without the `v` (`2026.10.1`).
- Bump it in all three `App/Info-*.plist` files, `MARKETING_VERSION` in
  `project.yml` and the assertion in `AppConfigurationTests`.
- `CFBundleVersion` (`CURRENT_PROJECT_VERSION`) stays the build number.
- The version also goes out as `X-Happy-Client: ios/2026.10.1`. The
  server uses it only for metrics labels.

## Conventions

- Swift 6 language mode and strict concurrency. UI is `@MainActor`;
  network and sync code is actors and `Sendable` values.
- Property observers don't run for assignments in a class's own
  initializer, even after `super.init`. A view whose `didSet` updates
  its subviews must call the same update from its init, as
  `ItemRowView.apply()` does. Missing this once left Settings and Server
  as empty cards. `InitialStateTests` checks the shared components.
- Tests use fakes, never the network:
  - `FakeHTTP` and `FakeWebSocket` in `Tests/HappyCoreTests/Fakes.swift`;
  - in-memory GRDB stores.
- Crypto changes must keep passing the tweetnacl vectors in
  `Tests/HappyCryptoTests/Fixtures/crypto-vectors.json`. Regenerate them
  with `scripts/generate-crypto-vectors.mjs` only if the format itself
  changes.
- Don't add a dependency without saying why in the PR. Current ones:
  - GRDB;
  - swift-crypto, Linux only;
  - swift-asn1, which swift-crypto pulls in.

## Open questions

- The RN app still sends legacy `role: 'user'` message envelopes. This app
  speaks only the session protocol. Confirm the server and CLI accept
  session-protocol user messages from phones before chat lands.
- `happy-wire`'s session protocol is marked frozen. Confirm it is the
  long-term format, not a transitional one.
- Closed: upgrading in place from the RN app. Credentials share
  expo-secure-store's item; see Scope. The logic is tested on Linux, but a
  real upgrade from an RN build on a device has not been tried yet.
- The shared item is `WhenUnlocked`, as the RN app wrote it. A cold launch
  in the background while the phone is locked therefore can't read the
  credentials, which matters once background sync exists.
- Deletions:
  - Sessions are reconciled by a daily full listing, because the API has
    no tombstone or "deleted since" feed. A server-side deletion feed
    would remove that.
  - Machines have no delta endpoint and are fetched in full.
- Deployment target is iOS 17. It is needed for the
  `registerForTraitChanges` and `keyboardLayoutGuide` APIs, among others.
- Terminals that only speak auth v1 (which hands over the master secret)
  are refused with an "update Happy" message. happy-app still accepts them.
- happy-app's `normalizeSecretKey` treats any input containing `-` as the
  formatted backup. A raw base64url secret can contain `-`, so the app
  misreads it. `SecretKeyBackup.normalize` recognizes the 43-character raw
  form first.
- Text sizes are fixed. Dynamic Type scaling, which RN applies by default,
  is not wired yet.
- Not ported yet from the onboarding screens:
  - the machine screen that Troubleshoot's computer rows open in
    happy-app (the rows are inert here);
  - copying terminal commands by selecting them.
