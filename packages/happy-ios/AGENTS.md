# happy-ios

Native iOS client for Happy, written in Swift with UIKit. It ports
`packages/happy-app` (React Native) screen by screen. It is not shipped yet:
nothing here is wired to the release skill or to EAS.

## Rules

1. **UIKit only, never SwiftUI.** No Core Data, SwiftData or CloudKit.
   Persistence is SQLite through GRDB (or raw SQLite).
2. **Dependencies come through SwiftPM only.** Never CocoaPods, Carthage or
   vendored frameworks.
3. **Build and test with `xtool` and `swift` on machines that aren't Macs.**
   On a Mac, use Xcode.
4. **The Xcode project is generated by XcodeGen from `project.yml`.** Never
   commit a `.xcodeproj` or edit one by hand.
5. **Measure every component and test its layout.** Layout is deterministic
   manual frame layout:
   - `HappyLayout` holds the layout logic. It is pure Swift and imports only
     Foundation, plus CoreGraphics on Apple platforms. Each layout is a
     function from inputs (container size, safe-area insets, measured
     content sizes) to frames.
   - Views in `HappyUI` only measure their content (`sizeThatFits`) and
     apply the computed frames in `layoutSubviews`. A view must not contain
     arithmetic that decides where something goes.
   - Every layout has exact-frame tests in `Tests/HappyLayoutTests`. They
     run on Linux.
   - Anything that needs UIKit to measure goes in `Tests/HappyUIKitTests`.
     That target compiles to nothing on Linux and runs only in the iOS
     simulator.
6. **No icon fonts.** Icons are happy-app's glyphs as vector outlines
   (`HappyIcons`), drawn as template images. Keep the fonts' license
   notices in `Sources/HappyIcons/LICENSES.md`.
7. **Telegram-iOS is a reference, never a source.** It is GPL-2.0. Study
   its techniques (async text layout, bubble animations, keyboard
   handling) and reimplement them; never copy its code, and don't depend
   on AsyncDisplayKit/Texture or its Display framework.
8. **Sync never runs on the main thread. The main thread only applies a
   minimal changeset that was computed elsewhere.**
   - Everything else runs off the main thread: network, decryption,
     decoding, merges and DB writes, the reducer, markdown and syntax
     highlighting, row-model derivation, diffing, and measurement.
   - In debug builds, sync, store and reducer entry points assert
     `dispatchPrecondition(condition: .notOnQueue(.main))`. UI apply points
     assert `.onQueue(.main)`.
   - Heartbeats are presence, not data. `activity` ephemerals update an
     in-memory presence actor per account. The UI hears about presence only
     when something it renders changes: `active` or `thinking` flips, or the
     shown text changes at its display granularity. Presence reaches SQLite
     only on a flip, on background or terminate, and at most about once a
     minute. Never write it once per heartbeat.
   - Merges skip unchanged rows (`updateChanges`), so a no-op write commits
     nothing and wakes no observer. A catch-up is batched, so many pages
     make one observable commit per batch, not one per page.
   - Observation is region-scoped. Fetching, deriving and `removeDuplicates`
     all happen off the main thread. There is one shared observation per
     account and region, not one per screen.
   - UI updates are minimal:
     - Row models are `Equatable` and diffed old against new.
     - A changed row is reconfigured in place, never reloaded.
     - Insert, delete or move only when membership or order changes.
     - At most one apply per frame or batch.
     - A field nothing renders never causes an apply.
     - No full reload after the first load.
   - Main-thread budgets:
     - at most 1 ms per typical delta;
     - at most 4 ms to apply a 1000-session catch-up;
     - no single block longer than half a 120 Hz frame (4.2 ms).

     Every main-thread apply sits inside an `os_signpost` interval. Debug
     builds count main-thread milliseconds per sync batch.
   - Linux tests guard all of this:
     - benchmarks over fixed fixtures, asserting operation counts exactly
       and wall time against a ceiling;
     - changeset tests asserting exactly which rows a change touches. For
       example, one session changed reconfigures exactly one row, a change
       to an unrendered field touches none, a 500-record catch-up is one
       apply, and a streamed token re-measures only the last bubble.

     A change that adds work to a sync path keeps them green.

## Scope

- **The current Happy protocol, meaning what the current CLI, happy-app
  and happy-agent actually exchange today** (not what the files are
  called). `packages/happy-wire`, happy-app's sync code
  (`packages/happy-app/sources/sync`) and the CLI's routing are the source
  of truth; when they disagree with this package, this package is wrong.
  - **User text goes out as `role: 'user'` records**,
    `{ role: 'user', content: { type: 'text', text }, meta }`, field for
    field as `sync.ts` `sendMessage` builds them, every meta field
    included (sentFrom, the delivery meta, appendSystemPrompt,
    permissionMode, model, modelProviderId, effort, serviceTier,
    displayText). A byte-compatibility test pins it against what `sync.ts`
    produces.
  - **Attachments go out as session-protocol `file` events**, sent before
    the text they belong to (`sync.ts:809`).
  - **Agent output arrives as session-protocol envelopes**
    (`role: 'session'`).
  - **No legacy paths.** There are no decoders for formats the current CLI
    no longer emits. Such records in old sessions render as a compact
    "unsupported message" placeholder, never as a crash or a silent gap.
    The chat reducer documents which record kinds are current and which
    are retired.
  - **The session protocol is not extended.** happy-wire marks it frozen
    ("do not add new consumers"), so this app consumes only what happy-app
    consumes and adds no new user-message shapes.
  - Encoding a user message is one function. If the session protocol is
    redesigned (its header mentions aligning with pi.dev), that function is
    the one to switch.
- **Every happy-app feature an iPhone user can reach**, tracked in
  [`docs/FEATURES.md`](docs/FEATURES.md). Excluded on purpose, with the
  reasons in that file:
  - anything gated by the `experiments` setting: the Usage page and the
    Rig file browser in the chat;
  - developer tools and every `dev/*` screen;
  - friends, user profiles, the inbox and the feed, which an iPhone can't
    reach in happy-app;
  - artifacts and the recent-sessions screen, which have no entry point;
  - web and desktop-only UI (command palette, shortcut hints, sidebar
    navigator, web tab bar), purchases and analytics.
- **Voice mode is included by the current product request.** The official
  ElevenLabs Swift SDK provides WebRTC microphone and speaker transport.
  Happy's authenticated backend alone grants its free or subscribed allowance;
  a missing client RevenueCat configuration never prevents a valid grant.
  Voice stops on background, account switch/sign-out, audio interruption or
  headphone removal. Client tools use the existing outbox and permission RPCs.
- **Offline first.** Everything the account has is kept in the local
  SQLite store, and the UI reads only from that store. The network only
  moves deltas:
  - sessions changed since a cursor;
  - messages after a session's last synced `seq`;
  - versioned settings, changed locally as a pending delta that is pushed
    with `expectedVersion` and re-based on the server's copy on conflict;
  - the profile and the projects sessions point at, fetched whole;
  - an idempotent outbox for writes.
- **Writes are optimistic.** A message is stored in the outbox and shows in
  the chat at once; delivery retries with backoff, and a failed item stays
  visible until retried or discarded. Settings use the pending delta above.
  - Sending pauses new network operations in the background and retains the
    outbox across suspension/relaunch. Foreground and reconnect resume it.
    In-flight operations finish under a UIKit background-task lease supplied
    through `SyncEngine.Options.deliveryActivity`; HappyCore imports no UIKit.
    Unlike happy-app's 30-second watchdog, suspension never fails or deletes
    accepted writes. A cancelled operation returns to queued with its localId.
  - A failed text/POST blocks later sends in that session; those remain queued.
    A failed attachment upload stays visible but is skipped so its text sends.
    Retry is idempotent by localId, including after a lost acknowledgement.
  - Unsupported permission modes are refused before acceptance: `send` throws
    `UnsupportedPermissionModeError`, and nothing is enqueued or copied.
- **Tool outputs are hidden by default** in the chat. This deliberately
  differs from happy-app: tool output is collapsed by default, tap to expand,
  and pending decisions stay open. Every tool row shows its header only
  (title, icon, status, timer, subtitle). Tapping the header opens its body
  in place, for the screen's lifetime, never persisted. While a permission
  is pending, or a question or plan awaits an answer, the input needed to
  decide stays open, but never the output. The synced `compactToolCalls`
  setting is untouched: it still picks a compact row or a card. Decided in
  `ChatToolPresentation` (`ToolDisplayState`).
- **The agent question sheet keeps "Send answer" above the keyboard.**
  happy-app's AgentQuestionModal leaves its footer at the bottom of the
  screen, under the keyboard. Here the footer rides the keyboard, so someone
  typing their own answer can send it without dismissing the keyboard first.
  Laid out in `QuestionSheetLayout`.
- **A message's own screen always scrolls, and Write's diff keeps its
  gutter there.** happy-app shows a text message in a plain View, so a long
  one is cut off, and WriteView's full-width section pulls 12 past each
  edge, which on a phone (no padding for edits) clips the line numbers.
  Here text scrolls and Write's diff sits edge to edge like Edit's. Built
  in `MessageDetailRenderer`.
- **The CLI-outdated pill sits under the header on every device.** happy-app
  places it 8 below the top of the content area. On a phone in portrait that
  area runs under the floating header, so the pill ends up behind the header
  and the status bar. Here it sits 8 under the navigation bar, where happy-app
  puts it on a tablet. Laid out in `CliWarningPillLayout`.
- **Push notifications follow happy-app's iPhone behaviour**
  (`sync/pushRegistration.ts`, `app/_layout.tsx`). They are wired in
  `Sources/HappyApp/PushNotifications.swift`, and the logic lives in
  `Core/Push/`.
  - **Registration.** The server sends through Expo, so the app registers
    an Expo token. `ExpoDevicePushTokenSource` exchanges the APNs bytes
    together with three other inputs:
    - expo-notifications' installation id (`ExpoInstallationID`), read from
      the RN build's own Keychain item and never replaced;
    - the APNs environment from `embedded.mobileprovision`
      (`ProvisioningProfile`);
    - the bundle id.
  - **When it syncs.** `PushTokenSync` ports `pushTokenSync`. It runs when
    the active account's session starts (sign-in, restore, switch, or the
    next account taking over after a sign-out) and on every
    app-became-active. It asks for permission while iOS still can, so the
    first sign-in prompts. Runs coalesce like `InvalidateSync`.
  - **Several accounts.** Only the active account registers, and its
    `LocalSettings` caches the token: each account change builds a new
    `TokenPushRegistration` and sets `SettingsHooks.pushRegistration`.
    Switching never unregisters, so every signed-in account keeps
    notifying. Sign-out removes the token from that account's own server
    with that account's own credentials, as `AuthContext.tsx` `logout`
    does, but never from a server the user hasn't confirmed.
  - **Presentation.** In the foreground a push only sets the badge and goes
    in the list. When the app is inactive or in the background, it shows
    in full.
  - **Opening.** A tap (default action only, once per request id) reads
    `sessionId`, or a `url` naming `/session/<id>`, from the payload's
    `body`, then calls `AppCoordinator.openSession(fromNotification:)`:
    - if another signed-in account's store holds the session
      (`AccountController.accountHoldingSession`), the app switches to that
      account first;
    - if no store holds it, it opens in the active account;
    - the stack becomes home, then the chat, unless that chat is already
      on top.

    A tap that launches the app waits for the stored account. One that
    needs a switch also waits for the restored account's first sync, which
    holds the account controller.
  - **Deliberate differences from happy-app:**
    - happy-app's backoff retries the server calls forever. Here each sync
      makes one registration attempt, and the next session start or
      foreground tries again.
    - The sign-out unregister is one attempt capped at 5 seconds, where
      happy-app holds logout until the server answers.
    - Concurrent APNs requests share one callback, where expo rejects the
      older request.
    - Expo's background re-registration when APNs rotates the token is not
      ported; the next foreground registers the new token.
    - Opening an already visible chat does nothing, where happy-app pushes
      a second copy.
    - The background-send watchdog's local notifications don't exist (see
      Offline first).
  - **Signing.** All three variants have `aps-environment` "development"
    and the `remote-notification` background mode, as the RN app's
    expo-notifications plugin writes them. Distribution signing swaps in
    the profile's "production".
- **Onboarding follows happy-app step by step.** Signed in, home decides
  from the stored machines (`HomeState`, after happy-app's
  `shouldShowFirstRunInstall` and `resolveHomeEmptyState`):
  - a spinner until machines have been fetched once. An empty store is
    "not known yet", so an account restored or upgraded from the RN app
    is never asked to link a computer it already has;
  - Link Your Computer when there are none;
  - the offline checklist when none is reachable and nothing is listed
    (with "Show archived" when there is an archive);
  - "No sessions yet" on a reachable computer with no sessions;
  - the session list otherwise, even while every computer is offline (the
    offline plaque heads it then).

  The session list is a `UITableView` over `SessionList` (happy-app's flat
  grouping): live rows by activity, the archive toggle, archived rows by
  day. Swipe or long press archives (`SessionActions`: `killSession` over
  `rpc-call`, then `POST /v1/sessions/:id/archive`). A tap only marks the
  row read until chat lands. Local-only row state (`thinking`, `unread`,
  `archiving`) lives on the session row and follows `LocalStore.settle`.

  Home stays the navigation root and swaps its content, so screens pushed
  over it stay put when a computer arrives.
- **Accounts.** Several accounts can be signed in; one is active at a time
  and switching is global (the whole UI follows the active account). The
  design, which the Accounts workstream implements:
  - **Credentials.** The RN app's item (`app:no-auth` /
    `auth_credentials`, described below) holds exactly one account, the
    *shared* account. It is never overwritten with another account's
    credentials and never deleted except by signing that account out.
    Every other account has its own generic-password item: service
    `happy-ios:account`, account = the account id, same accessibility.
    Signing in a new account writes the shared item only when it is empty;
    otherwise the account gets its own item. Signing the same account in
    again updates the item that already holds it.
  - **Registry.** The list of accounts (id, server URL, which item holds
    the credentials, the order they were added, the active one) lives in
    `Application Support/Happy/accounts.json`. It holds no secrets. On
    launch, a shared item that the registry doesn't know (the RN app's,
    after an upgrade) is imported as an account, never copied.
    Writes are atomic. Missing credentials drop an entry; corrupt JSON is
    rebuilt by enumerating the secondary Keychain service and reading the
    shared item. Keychain access errors leave the registry untouched.
  - **Servers.** Auth uses the active session's server while signed in,
    or the `ServerConfig` candidate while adding an account or signed out.
    Every session uses its account's registry URL. Secondary items store a
    JSON envelope with `credentials` and `serverURL`, so recovery after a
    corrupt registry retains their servers. The shared item's layout stays
    unchanged. Importing an unknown shared account reads RN's unencrypted
    `Documents/mmkv/server-config` and `.crc` metadata without writing them.
    The decoder verifies CRC32, honors metadata actual size, and replays
    append-only map records. A missing file/key or empty value selects the
    default server, never the global native candidate. Invalid data or URL
    sets `serverConfirmed: false`: no session, HTTP, or socket may use that
    account until `confirmServer(_:for:)` validates and persists the host.
    `pendingServerConfirmation` drives a server form as the navigation root.
  - **Switcher display and observation.** Nonsecret name, GitHub login
    (`username`), avatar URL and thumbhash are cached in the registry from
    each account's `accountProfile` row. Recovery seeds these fields through
    read-only database access; the active profile is observed for updates.
    `observeAccounts(_:)` delivers an immediate snapshot and independent
    updates on add, removal, switch, and profile changes. Keep its
    `AccountsObservation` token alive; releasing or cancelling it stops
    delivery. `localSettings` is replaced on switch, so read it again and
    reapply the active account's theme after an account update.
  - **Adding and logout.** `beginAddingAccount()` marks onboarding as an
    add flow while retaining the active session; `cancelAddingAccount()`
    leaves it intact. `signIn(_:)` always adds/reauthenticates and activates
    without signing other accounts out. `signOut()` removes only the active
    account; `signOut(accountID:)` can remove an inactive one. The next
    account in added order becomes active when the active one signs out.
    The UI root changes before the removed account's store is erased and
    files deleted. Signed-out logout never deletes unknown RN bytes. If RN
    authenticates an account also held in an own item, recovery removes that
    redundant own item only after reading the shared credentials successfully.
  - **Account id.** The account's anonymous id, derived from its secret,
    so it is known offline and the same account is never listed twice.
  - **Separate caches.** Each account has its own directory,
    `Application Support/Happy/accounts/<id>/`, holding its SQLite store
    (`store.sqlite`), attachment files (`files/`) and anything else
    cached for it. Device-only settings that belong to an account live in
    a per-account defaults suite. Nothing is shared between accounts.
    `AccountSession.filesDirectory` exposes `files/`. The old
    `Happy/happy-<id>.sqlite` and its WAL/SHM sidecars move into the account
    directory on first open, before SQLite opens the new path.
  - **Switching** stops the active account's sync and socket, opens the
    other account's store (its home shows from disk at once) and starts
    its sync. Only the active account syncs.
  - **The Server screen** (`ServerConfigViewController`) edits only the
    candidate used to sign in or add an account. An existing account's
    server changes only through the confirmation flow.
  - **What an RN rollback sees.** The RN build reads only the shared item,
    so it comes back signed in to the shared account and knows nothing of
    the others. Their items and caches stay on disk, unused, and are picked
    up again when this app is reinstalled. If the shared account was
    signed out here, the RN build starts signed out.
- **Credentials stay in the RN app's Keychain item.** This app reads and
  writes happy-app's `auth_credentials` exactly as expo-secure-store 55
  stores it, so an in-place upgrade (same bundle ids) stays signed in and a
  rollback to an RN build still works for the shared account. Never copy
  shared credentials into an item of our own, and don't change its layout
  (secondary accounts use the separate service described above):
  - generic password, service `app:no-auth`;
  - account and generic set to the UTF-8 bytes of `auth_credentials`;
  - `kSecAttrAccessibleWhenUnlocked`, the default access group;
  - the value is the UTF-8 of `JSON.stringify({ token, secret })`.

  Reads go `app:no-auth`, then `app:auth`, then legacy `app`. Writes add to
  `app:no-auth` (updating on a duplicate) and then delete the other two.
  Logout deletes all three. `Sources/HappyCore/Auth/SecureStore.swift`
  implements this behind `KeychainBackend`, and `SecureStoreTests` pins it
  on Linux. Any other iOS-only secret gets its own item and must never
  touch this one.
- **Copy comes from happy-app.** English strings are copied verbatim from
  `packages/happy-app/sources/text/translations/en.ts` into
  `Sources/HappyUI/Strings.swift`.
- **Design tokens come from happy-app.** They are ported from `theme.ts`
  and the component stylesheets (iOS values) into
  `Sources/HappyLayout/DesignTokens.swift`.

`LocalChatFeed` reads disk first, observes a small session/count/outbox value,
and fetches only message rows inserted after its SQLite rowid cursor. This
handles socket records arriving before lower-sequence delta records. Message
deletion rebuilds the reducer; normal append, permission and outbox updates do
not. Outbox rows are a removable overlay and delivery state comes from schema
v3. Usage and todos travel on `ChatSnapshot` for the composer and chat.
Tool outcomes and sidechain children whose calls or owners have not reached
disk yet are buffered across batches and joined when their missing records
arrive. This deliberately improves on the RN reducer's discarded early
results, because rowid-based replay can fill a sequence gap in a later batch.
Activity, unread, archive and unrelated metadata changes are excluded from
the observed session projection. Equal visible snapshots are not re-emitted.

- `HappyApp` is the app that xtool packages.

  `Sources/HappyApp` itself and links `HappyKit`.

## Build and test

### Linux

The toolchain is Swift 6.x. The GRDB build needs the `libsqlite3-dev`
headers.

```sh
swift build --build-system native
swift test --build-system native         # everything except HappyUIKitTests
```

`--build-system native` is used because the newer swiftbuild backend has
been seen to hang in sandboxes.

To build for iOS with the Darwin SDK from `xtool sdk`:

```sh
swift build --build-system native --swift-sdk arm64-apple-ios
swift build --build-system native --swift-sdk arm64-apple-ios-simulator --build-tests
xtool dev build                          # packages xtool/HappyApp.app (dev bundle id)
xtool dev run                            # needs `xtool auth` and a connected device
```

xtool reads `xtool.yml` and packages the dev variant only. Notes:

- If SwiftPM can't find the SDK (it resolves `~` through the passwd
  entry), pass `--swift-sdks-path <dir containing darwin.artifactbundle>`.
- xtool has no test runner and Linux has no simulator, so
  `HappyUIKitTests` can be built here but not run.

### macOS

```sh
brew install xcodegen
xcodegen                                 # writes Happy.xcodeproj (git-ignored)
open Happy.xcodeproj
```

### Variants

| Variant | Configuration | Bundle id | Name |
| --- | --- | --- | --- |
| development | Debug | `com.slopus.happy.dev` | Happy v2 (dev) |
| preview | Preview | `com.slopus.happy.preview` | Happy v2 (preview) |

The bundle ids are the RN app's. Each variant has its own
`App/Info-*.plist`. Those files are plain plists, because xtool doesn't
expand `$(VARIABLES)`. `AppConfigurationTests` keeps their shared keys
identical and checks the variant keys:

- display name;
- `HappyAppVariant`;
- ATS: local networking everywhere, arbitrary loads outside production.

Only production has entitlements (associated domains).

### Versioning

This app uses a new versioning scheme, separate from happy-app's semver
(`1.x.y`): **`vYYYY.MM.N`**, where `N` counts releases within that month,
starting at 1 (e.g. `v2026.10.1`). The "v2" in the display names likewise
tells it apart from the legacy RN app.

- `CFBundleShortVersionString` must be integers only, so it holds the
  version without the `v` (`2026.10.1`).
- Bump it in all three `App/Info-*.plist` files, `MARKETING_VERSION` in
  `project.yml` and the assertion in `AppConfigurationTests`.
- `CFBundleVersion` (`CURRENT_PROJECT_VERSION`) stays the build number.
- The version also goes out as `X-Happy-Client: ios/2026.10.1`. The
  server uses it only for metrics labels.

## Conventions

- Swift 6 language mode and strict concurrency. UI is `@MainActor`;
  network and sync code is actors and `Sendable` values.
- Property observers don't run for assignments in a class's own
  initializer, even after `super.init`. A view whose `didSet` updates
  its subviews must call the same update from its init, as
  `ItemRowView.apply()` does. Missing this once left Settings and Server
  as empty cards. `InitialStateTests` checks the shared components.
- Tests use fakes, never the network:
  - `FakeHTTP` and `FakeWebSocket` in `Tests/HappyCoreTests/Fakes.swift`;
  - in-memory GRDB stores.
- Crypto changes must keep passing the tweetnacl vectors in
  `Tests/HappyCryptoTests/Fixtures/crypto-vectors.json`. Regenerate them
  with `scripts/generate-crypto-vectors.mjs` only if the format itself
  changes.
- Don't add a dependency without saying why in the PR. Current ones:
  - GRDB;
  - swift-crypto, Linux only;
  - swift-asn1, which swift-crypto pulls in.

## Workstreams

The port is built by parallel workers, each on its own branch, merged into
the integration branch by the coordinator. A worker owns its files; to
change a file another workstream owns, ask the coordinator.

Shared seams, changed only through the coordinator:

- `Sources/HappyCore/Chat/ChatMessage.swift` and `ChatContracts.swift`:
  the reducer produces `ChatMessage`, the UI reads `ChatSnapshot` from a
  `ChatFeed` and sends through `ChatSending`;
- `Sources/HappyUI/Chat/ChatComposer.swift`: the chat screen hosts
  whatever `ChatComposerFactory.make` returns (a `ChatComposerView`),
  feeds it `ChatComposerState` and re-lays out on
  `composerDidInvalidateHeight`; the composer never handles the
  keyboard. The Composer workstream swaps only the one line in
  `ChatComposerFactory.make`;
- `SessionActions` (permission, abort, questions, archive);
- `AccountController.accounts` and `switchAccount(to:)`;
- `Sources/HappyUI/Navigation/Route.swift`: screens open each other only
  through `push(_ route:context:)`. Each workstream replaces only its own
  placeholders in `Screens.make`;
- the iPad shell: the window's root is `TabletShellViewController`, which
  embeds `AppCoordinator`'s navigation controller as its detail and is
  that controller's delegate, so nothing else sets `navigation.delegate`.
  Tablet branches read `traitCollection.isTabletLayout` and `isZenMode`
  (re-laid out through `registerForTraitChanges([TabletLayoutTrait.self])`);
  their rules are in `HappyLayout/Tablet/TabletBranches.swift`;
- `Schema.swift`: migrations are added by the Sending workstream or the
  coordinator. Migrations are append-only now that Preview has shipped;
  never change a registered migration.

To keep parallel work from colliding:

- New strings go in a file of their own, `Sources/HappyUI/Strings/<Area>.swift`,
  as `extension Strings { enum <Area> { … } }`, still copied verbatim from
  en.ts. Don't append to `Strings.swift`.
- New tokens go in `Sources/HappyLayout/Tokens/<Area>Tokens.swift` as
  extensions of `Palette`, `TextStyles` and friends. Don't append to
  `DesignTokens.swift`.
- Tests go in new files named after the area.

## Open questions

- Closed: which user-message format to send. The CLI accepts only
  `role: 'user'` text records and session-protocol `file` events from a
  phone: `happy-cli/src/api/apiSession.ts:574` (`routeIncomingMessage`)
  tries `UserMessageSchema` and `FileEventMessageSchema` and nothing else.
  Session-protocol user text would be dropped without an error. happy-app
  (`sync.ts:883`) and happy-agent (`src/session.ts:194`) send
  `role: 'user'`, and happy-wire's `sessionProtocol.ts` header says it is
  under review and frozen. Decision: send what they send (see Scope).
- Still open: the session protocol's long-term shape. Its header points at
  aligning with pi.dev. When it changes, switch the one encoding function.
- Closed: upgrading in place from the RN app. Credentials share
  expo-secure-store's item; see Scope. The logic is tested on Linux, but a
  real upgrade from an RN build on a device has not been tried yet.
- The shared item is `WhenUnlocked`, as the RN app wrote it. A cold launch
  in the background while the phone is locked therefore can't read the
  credentials, which matters once background sync exists.
- Deletions:
  - Sessions are reconciled by a daily full listing, because the API has
    no tombstone or "deleted since" feed. A server-side deletion feed
    would remove that.
  - Machines have no delta endpoint and are fetched in full.
- Deployment target is iOS 17. It is needed for the
  `registerForTraitChanges` and `keyboardLayoutGuide` APIs, among others.
- Terminals that only speak auth v1 (which hands over the master secret)
  are refused with an "update Happy" message. happy-app still accepts them.
- happy-app's `normalizeSecretKey` treats any input containing `-` as the
  formatted backup. A raw base64url secret can contain `-`, so the app
  misreads it. `SecretKeyBackup.normalize` recognizes the 43-character raw
  form first.
- Text sizes are fixed. Dynamic Type scaling, which RN applies by default,
  is not wired yet. happy-app sets no `allowFontScaling={false}`; the only
  cap is `maxFontSizeMultiplier={1.2}` on the onboarding titles
  (`OnboardingContent.tsx`), so every other text scales uncapped.
- Not verified anywhere yet: push delivery, presentation and taps,
  a run in the simulator or on a device,
  `HappyUIKitTests` (built, never run), and a real in-place upgrade from an
  RN build.
- Accounts import: the real-device MMKV path and decoding still need an
  in-place upgrade check. Encoding, size metadata, CRC and confirmation gates
  are verified on Linux with reproduced MMKV fixtures.
