# 输入区域变更原则

适用于 Paws 的普通会话、项目会话和新建会话，覆盖输入正文、输入框内部，以及与输入框连成一体的上下常驻区域。每次接到或更新需求，都先核对本原则；它不意味着所有功能改动都需要重新审批。

## 默认保持输入区域

输入区域用于用户表达要求和发送消息。新增功能不自动获得占用这里的授权。未经用户对**具体内容、呈现位置和触发方式**的明确确认，不得新增文字、按钮、卡片、标签、状态条或功能入口，也不得把系统生成内容擅自填入草稿。

“实现这个功能”“总体方案可以”“发布当前版本”不等于认可把入口放进输入框。不能用“便于发现”“统一入口”或“省去寻找”替代具体位置的确认；用户最新的否定与纠正优先于先前的总体肯定。

## 每次需求更新先核对

1. 这次是否会给输入区域新增内容、增加常驻高度或改变用户原有的输入与发送路径。
2. 若有增量，用户是否明确认可了这项内容、位置及其常驻或主动触发方式；只复用仍然有效的具体决定。
3. 未获认可时保持输入区域原样，沿用该功能已有的侧栏、项目页或工作区入口。确实必须改输入区域时，先给出原位、可审阅的增量方案，只确认缺失部分。
4. 已有具体确认或只是修复原有行为时直接推进，不借本原则重复询问整个需求、实现或发布。

## 保留已有上下文与用户动作

- 已确认的附件、文件引用、选中批注等沿用原契约；有对应用户动作或内容时出现，没有时不占一行。
- 用户明确选定的修改对象可以沿既有引用方式显示，不借此再常驻一块工程库或新增功能推广区。
- 删除未经确认的新入口，不顺带删除已经认可的引用、批注、权限、模型和发送能力。
- 不能把被否定的常驻条换个名字、移到输入框上方或塞进另一处输入控件，作为同一增量未经确认的替代实现。

## 验收

- 普通会话输入区域不出现与当前输入无关的新增块，也不保留其空白高度。
- 用户已选择的附件、引用与批注仍能按原流程显示、编辑、移除和发送。
- 被保留的原有侧栏或项目入口仍可进入功能；新增入口的位置与实际认可范围一致。
- 在需求和 PR 中明确本次输入区域增量及其确认依据；没有增量就写明沿用既有流程，不虚构用户认可。

本原则来自 2026-11-27 对影片工程入口的明确反馈：输入框内新增的「项目产物 / 关联产物」常驻块未获具体确认，应撤除。该反馈不是对其他已确认输入功能的撤销。
