# Paws 设计规范入口

设计、实现或评审用户可见界面前，先读本入口，再按本次改动展开相关规范。根 `CLAUDE.md` 负责要求遵循，具体规则归这里；代码中的主题、布局和组件仍是实现与取值的唯一来源。

## 每次设计前，先交代五件事

1. **所在场景**：平台、页面、所属工作区、可用宽度与用户正在完成的任务；PC 多栏和手机触控分别设计。
2. **复用依据**：该页面已有组件、字体、层级和布局约束；优先原位延续，避免单个新模块形成另一套风格。
3. **语义变量与背景所有者**：背景、文字、图标、边框、普通/交互/选中状态分别从哪个当前主题角色取值；谁绘制整栏背景，内部容器是否会覆盖皮肤或重复叠色；不只提供一张默认主题截图。
4. **状态与退出**：加载、空、错误、禁用、选中、焦点、离线，以及关闭/返回时要保留的输入、选择和阅读位置。
5. **验证范围**：哪些主题、状态、断点和真实交互需要检查，哪些证据尚未取得。

这些内容可简写进需求、组件说明或 PR；小改动只补相关项，不为形式生成整套设计文档。

## 统一完成标准

- 新界面与原页面的层级、密度、交互语义一致；用户能发现主要动作、看到当前状态并退出。
- 使用当前主题的语义变量，明暗态及至少一个非默认深色主题不残留默认色；新增角色在源码的完整主题链路中定义。
- 使用已有布局和组件；字号、间距、圆角、图标与点击范围各自有依据，不用减小文字掩盖布局问题。
- 必需信息不只靠颜色、hover 或图标传递；键盘、屏幕阅读器与触控方式有对应入口和反馈。
- 按风险完成必要测试/真实交互验证。截图需求沿根 `CLAUDE.md` 当前约定，不将未请求截图自动设为门禁。
- 区分规范、源码检查、隔离测试、真实页面和用户设备证据；设计文档存在不等于所有历史页面已符合。

## 如何持续沉淀

- 可跨功能复用的稳定规则进入本目录；具体功能布局进入专用设计文档；缺陷、复现和运行证据进入 `docs/validation/`。不要把一次修复的全部流水写进规范。
- 变量名、默认值、主题数量和组件能力改变时，更新相关链接与说明；不维护另一套手抄色值和尺寸表。
- 发现反复出现的交互/视觉错误时，补齐“适用范围 → 原因 → 正确做法 → 验收方式”，并在本入口添加导航。
- 产品专属规则归本仓库；Design OPS 保存通用方法和定位入口，不复制第二份 Paws 规范作为事实源。
